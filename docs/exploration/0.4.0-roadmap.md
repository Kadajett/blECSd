# blECSd 0.4.0 Improvement Roadmap

> **Status:** Final | **Date:** 2026-02-13
> **Based on:** Competitive analysis of 14 libraries across 8 languages (see `competitive-analysis.md`), plus deep codebase gap analysis

## Executive Summary

blECSd 0.4.0 already ships three major architectural features: plugin/module system, CSS-like stylesheet system, and 2D render backend abstraction. This roadmap identifies additional improvements to close gaps with competitors while leveraging blECSd's unique ECS architecture as a differentiator.

**Key theme:** Make blECSd the most capable TypeScript terminal UI library by combining ECS-native performance with the developer experience polish that Textual, Ratatui, and Bubbletea have set as the standard.

**Critical insight from competitive analysis:** The researcher's comparison matrix incorrectly marked several blECSd features as missing (tree view, text area, modal dialogs, virtual scrolling, command palette, theming, multi-select, charts) that we already have. This reveals a **discoverability problem**: our existing capabilities are not obvious from docs or API surface. Improving documentation, examples, and API ergonomics may deliver more adoption value than new features alone.

## Current State (0.4.0 Baseline)

### Already Shipped in 0.4.0
- Plugin/module system for extensible architecture
- CSS-like stylesheet system with selector cascading
- 2D TUI render backend abstraction (ANSI + Kitty)
- Calendar widget
- Packed entity store adapter (performance optimization)

## Priority Tiers

### P0: Must-Have (Ship in 0.4.0)

These close critical gaps that would prevent adoption by serious projects.

#### 1. Search/Grep in VirtualizedList
- **What:** Add regex and literal search within VirtualizedList content, with match highlighting, next/prev navigation, and match count display
- **Why:** Every log viewer, code viewer, and data inspector needs search. VirtualizedList handles 10M+ lines but has zero search capability. This is the #1 missing feature for the flagship widget.
- **Competitor inspiration:** Ratatui ecosystem has `tui-textarea` with search; Textual's `TextArea` has built-in find/replace; even basic `less` has `/pattern`
- **Complexity:** Medium (3-5 days)
- **ECS advantage:** Search results can be stored as components on the list entity, enabling systems to react to match state changes (e.g., auto-scroll to matches, highlight rendering)
- **Implementation notes:**
  - Add `SearchState` component: query, matches (line indices), current match index, regex flag
  - Add search methods to VirtualizedList widget: `search(query, options)`, `nextMatch()`, `prevMatch()`, `clearSearch()`
  - Integrate with Vi mode's existing `/` search activation
  - Support both regex and literal modes
  - Display match count in scrollbar or status area

#### 2. Enhanced Multi-Select UX
- **What:** Improve multi-select in List widget with range selection (Shift+arrow), toggle-all, invert selection, and visual indicators (checkboxes/markers)
- **Why:** Multi-select exists but is primitive. No range selection, no visual feedback beyond highlight. Power users expect Shift+click ranges and Ctrl+A.
- **Competitor inspiration:** Textual's `SelectionList` with rich checkboxes; Bubbletea's `list` bubble with multi-select indicators
- **Complexity:** Low-Medium (2-3 days)
- **Implementation notes:**
  - Add `SelectionRange` component for tracking range anchors
  - Add keyboard shortcuts: Space (toggle), Shift+Up/Down (extend range), Ctrl+A (all), Ctrl+D (none)
  - Render checkboxes `[x]`/`[ ]` or bullet markers for selected items
  - Emit batch selection events (not one per item)

#### 3. Command Palette Enhancements
- **What:** Add rendered category grouping, recent commands, keyboard shortcut rendering, and prefix modes (`:` for commands, `>` for files, `@` for symbols)
- **Why:** CommandPalette exists but renders flat. No visual category headers, no MRU, no prefix-mode switching. VS Code's palette is the gold standard users expect.
- **Competitor inspiration:** VS Code command palette (the universal benchmark); Warp terminal's command palette with context-aware modes
- **Complexity:** Medium (3-4 days)
- **Implementation notes:**
  - Add category header rendering with separator lines
  - Track recent commands in a bounded LRU list
  - Support prefix modes: bare text = fuzzy all, `:` = commands only, `>` = file picker, `@` = symbol jump
  - Show keyboard shortcuts right-aligned with dimmed style
  - Add `onModeChange` callback for prefix mode transitions

#### 4. Accessibility Foundation
- **What:** Add ARIA-like role and label components, focus ring visualization, and screen reader announcement support via terminal bell/title
- **Why:** No TUI framework does accessibility well, but Textual is starting to invest. Being first to market with a systematic approach is a massive differentiator.
- **Competitor inspiration:** Textual has basic accessibility testing; Web ARIA patterns; WCAG terminal adaptation
- **Complexity:** Medium-High (4-6 days)
- **ECS advantage:** Accessibility is naturally composable with ECS. Add `AccessibleLabel`, `AccessibleRole`, `AccessibleDescription` components to any entity. A `screenReaderSystem` can query all focusable entities and announce labels via terminal title bar or bell.
- **Implementation notes:**
  - `AccessibleRole` component: button, checkbox, list, listitem, textbox, dialog, etc.
  - `AccessibleLabel` component: human-readable label for screen readers
  - Focus ring rendering (visible outline on focused element)
  - `announce(message)` function that uses terminal title bar or OSC sequences
  - High-contrast theme variant (already have theme system)

### P1: Should-Have (Ship in 0.4.0 or 0.4.1)

These significantly improve developer experience and fill important widget gaps.

#### 5. Data Table with Sort/Filter/Paginate
- **What:** Enhanced table widget with column sorting (click header), column filtering, pagination, and column resizing
- **Why:** ListTable exists but is static. Real applications need sortable, filterable data tables. This is table stakes (pun intended) for dashboards.
- **Competitor inspiration:** Textual's `DataTable` widget with sort indicators and column selection; Ratatui's `Table` with `TableState` for scroll/selection tracking
- **Complexity:** High (5-7 days)
- **ECS advantage:** Sort state, filter state, and pagination can each be separate components. Sorting system processes table entities independently. Column resize can use the drag system.
- **Implementation notes:**
  - Extend Table widget or create DataTable widget
  - Add `SortState` component: column index, direction (asc/desc/none)
  - Column headers are interactive (click to sort, drag to resize)
  - Built-in filter row below headers
  - Virtual scrolling for large datasets (integrate with VirtualViewport)

#### 6. Context Menu Widget
- **What:** Right-click or keybind-triggered popup menu with nested submenus, separators, keyboard shortcuts, and disabled items
- **Why:** No context menu widget exists. Every IDE-like application needs context menus. This is a major missing primitive.
- **Competitor inspiration:** Textual has no built-in context menu either (gap in all TUI frameworks); VS Code context menus
- **Complexity:** Medium (3-4 days)
- **Implementation notes:**
  - Factory: `createContextMenu(world, entity, config)`
  - Support nested submenus with arrow key navigation
  - Separator items and disabled items
  - Auto-positioning to avoid screen edge overflow
  - Dismiss on click-outside or Escape
  - Integrate with mouse right-click events

#### 7. Notification Center / Toast Queue
- **What:** Centralized notification manager that stacks toasts, supports priorities, handles overflow, and provides a persistent notification history panel
- **Why:** Toast widget exists but is standalone. No queue management, no stacking, no priority system. Real apps need centralized notification management.
- **Competitor inspiration:** VS Code notification center; macOS notification center pattern
- **Complexity:** Medium (3-4 days)
- **ECS advantage:** Each notification is an entity with `NotificationPriority`, `NotificationTimestamp`, and `NotificationDuration` components. A notification system manages layout, animation, and auto-dismiss.
- **Implementation notes:**
  - `createNotificationCenter(world, config)` factory
  - Auto-stacking with configurable max visible
  - Priority levels: error > warning > info
  - Persistent history panel (toggle with keybind)
  - Animation support for slide-in/fade-out (leverage existing animation system)

#### 8. Breadcrumb Widget
- **What:** Horizontal breadcrumb navigation showing path/hierarchy with clickable segments
- **Why:** FileManager, tree views, and any hierarchical navigation benefits from breadcrumbs. Common UI pattern with no TUI equivalent.
- **Competitor inspiration:** VS Code breadcrumb bar; web UI patterns
- **Complexity:** Low (1-2 days)
- **Implementation notes:**
  - `createBreadcrumb(world, entity, { items, separator, onClick })`
  - Arrow key navigation between segments
  - Truncation with ellipsis for long paths
  - Style support via theme system

#### 9. Status Bar Widget
- **What:** Enhanced status bar (beyond current Footer) with left/center/right zones, click handlers, and mode indicators
- **Why:** Footer is basic text. Applications like vim, tmux, and VS Code have rich status bars with interactive segments showing mode, file info, cursor position, etc.
- **Competitor inspiration:** Vim statusline; VS Code status bar; tmux status line
- **Complexity:** Low-Medium (2-3 days)
- **Implementation notes:**
  - `createStatusBar(world, entity, { left: [...], center: [...], right: [...] })`
  - Each segment is an entity with click handler
  - Dynamic content updates (e.g., line:col position)
  - Mode indicator integration (normal/insert/search from Vi mode)

#### 10. Improved Fuzzy Search Highlighting
- **What:** Visual highlighting of matched characters in fuzzy search results across all widgets that use fuzzy search (List, CommandPalette, Autocomplete)
- **Why:** fuzzySearch utility returns match indices but no widget renders the highlights. Users can't see which characters matched.
- **Competitor inspiration:** VS Code's fuzzy match highlighting; fzf's match coloring
- **Complexity:** Low (1-2 days)
- **Implementation notes:**
  - Create `renderFuzzyHighlight(text, indices, highlightStyle)` utility
  - Apply in List render, CommandPalette render, and Autocomplete render
  - Use bold or accent color for matched characters

#### 11. Spring-Physics Animation Primitives
- **What:** Add spring-physics animation support to the existing animation system (stiffness, damping, target value)
- **Why:** BubbleTea's Harmonica library and FTXUI both offer spring animations. Modern UIs feel more natural with spring-based motion than linear easing. blECSd already has an animation system and velocity components, but lacks spring dynamics specifically.
- **Competitor inspiration:** BubbleTea + Harmonica (Go); FTXUI (C++) built-in animations
- **Complexity:** Medium (3-4 days)
- **ECS advantage:** Spring state (stiffness, damping, target) maps perfectly to components. A `springSystem` processes all spring-animated entities each frame. Compose with existing `Velocity` and `Position` components.
- **Implementation notes:**
  - Add `SpringAnimation` component: stiffness, damping, targetX, targetY, velocityX, velocityY
  - Add `createSpring(world, eid, config)` helper
  - Integrate with existing `animationSystem` phase
  - Common presets: `springBouncy`, `springSmooth`, `springSnappy`

#### 12. Spatial Mapping for Visibility Culling
- **What:** Implement grid-based spatial partitioning for O(1) visibility checks (which entities are visible in a scrollable viewport)
- **Why:** Textual's spatial mapping algorithm enables constant-time visibility for 1000+ widgets. Our `visibilityCulling.ts` exists but could be enhanced with spatial hashing.
- **Competitor inspiration:** Textual's spatial mapping algorithm (detailed in their blog)
- **Complexity:** Medium (3-4 days)
- **ECS advantage:** `spatialHash.ts` system already exists. Extend it for viewport-based visibility queries.
- **Implementation notes:**
  - Enhance existing `spatialHash.ts` with viewport-aware query
  - Grid cell size = viewport dimensions
  - Register entities on position change
  - Query returns only entities overlapping current viewport

#### 13. Constraint-Based Layout Helpers
- **What:** Add constraint types (Length, Percentage, Min, Max, Ratio) as layout helpers alongside existing Flexbox/Grid
- **Why:** Ratatui's constraint system is praised for building responsive terminal layouts that auto-adapt to terminal resize. Our Flexbox/Grid cover many cases, but constraints are a more natural fit for terminal column splits.
- **Competitor inspiration:** Ratatui's constraint-based layout
- **Complexity:** Medium (3-4 days)
- **Implementation notes:**
  - `Constraint` type: `fixed(n)`, `percentage(p)`, `min(n)`, `max(n)`, `ratio(a, b)`
  - `layoutHorizontal(world, constraints, entities)` and `layoutVertical(world, constraints, entities)`
  - Integrates with existing layoutSystem

#### 14. Hot Reload for Stylesheets
- **What:** Watch `.blecsd.css` / stylesheet files for changes and apply them without restarting the application
- **Why:** Textual's CSS hot reload is cited as a "game-changer" for DX. We have the stylesheet system but no file watching.
- **Competitor inspiration:** Textual TCSS hot reload
- **Complexity:** Low-Medium (2-3 days)
- **Implementation notes:**
  - Use `fs.watch` on stylesheet files
  - Re-parse and re-apply on change
  - Emit `stylesheet:reload` event for user hooks

### P2: Nice-to-Have (0.4.x or 0.5.0)

These add polish and advanced capabilities.

#### 15. Drag-and-Drop for Lists/Trees
- **What:** Reorder items via keyboard (Alt+Up/Down) or mouse drag within List and Tree widgets
- **Why:** Drag system exists for panels but not for list item reordering. This enables sortable lists, priority queues, and tree reorganization.
- **Competitor inspiration:** macOS Finder list reordering; web drag-and-drop patterns
- **Complexity:** Medium-High (4-5 days)
- **ECS advantage:** Drag system already handles entity dragging. Extend it with `DragReorderTarget` component that snaps to list positions.

#### 16. Color Picker Widget
- **What:** Terminal color picker with palette view, HSL sliders, and hex input
- **Why:** Theme editing, configuration UIs, and design tools need color selection. No TUI framework has this.
- **Competitor inspiration:** Web color pickers adapted for terminal constraints
- **Complexity:** Medium (3-4 days)

#### 17. Internationalization (i18n) Support
- **What:** RTL text support, locale-aware number/date formatting, and translation key system
- **Why:** Terminal apps are used globally. RTL support is particularly important for Hebrew/Arabic users.
- **Competitor inspiration:** Web i18n patterns; ICU
- **Complexity:** High (5+ days)

#### 18. Inline Editing for Tables/Lists
- **What:** Double-click or Enter to edit cell/item values inline, with validation and commit/cancel
- **Why:** Enables spreadsheet-like editing and property panels. Currently requires separate prompt widgets.
- **Competitor inspiration:** VS Code settings editor; web editable tables
- **Complexity:** Medium (3-4 days)

#### 19. Snapshot/State Persistence
- **What:** Serialize/deserialize complete world state for session resumption
- **Why:** Terminal apps often need to restore state after suspend (Ctrl+Z) or between sessions.
- **Complexity:** Medium (3-4 days)
- **Implementation notes:** Core already has `serialization.ts`, extend to cover widget state maps

#### 20. Performance Dashboard Widget
- **What:** Built-in FPS counter, entity count, system timing, and memory usage display for development
- **Why:** DevTools exists but a lightweight performance overlay is useful during development
- **Competitor inspiration:** Game engine debug overlays
- **Complexity:** Low (1-2 days)

#### 21. Widget Ecosystem / Package Registry Foundation
- **What:** Documentation and tooling for third-party widget packages (npm @blecsd/ scope, widget template, registration protocol)
- **Why:** Ratatui has 2,200+ dependent crates; BubbleTea has 10,000+ apps. Community widgets are a force multiplier. Our plugin system exists but no ecosystem yet.
- **Competitor inspiration:** Ratatui ecosystem; npm component libraries
- **Complexity:** Medium (docs + tooling, 3-4 days)

#### 22. Showcase / Interactive Widget Gallery
- **What:** Terminal-native interactive demo that displays all widgets with live configuration
- **Why:** Ratatui has a beautiful widget showcase. An interactive gallery is the best documentation for a TUI library.
- **Competitor inspiration:** Ratatui showcase; Textual demo app
- **Complexity:** Medium (3-4 days)

## Architecture Recommendations

### ECS-Native Patterns to Emphasize

blECSd's ECS architecture is its primary differentiator. Every new feature should leverage this:

1. **Components over configuration:** Store widget state as components, not in Maps. This enables queries and systems to operate on state uniformly.
2. **Systems over methods:** Where possible, provide systems that batch-process entities rather than per-entity methods. Example: `searchSystem` that processes all searchable entities.
3. **Composition over features:** Instead of building a monolithic DataTable, compose it from List + SortState + FilterState + ColumnResize components.

### Theme System Integration

All new widgets MUST integrate with the existing theme system:
- Use `ThemeColors` for default styling
- Support `Stylesheet` selectors
- Respect high-contrast mode

### Plugin Architecture Leverage

Major features should be implementable as plugins:
- Accessibility could be a `@blecsd/a11y` plugin
- Advanced table features could be a `@blecsd/data-table` plugin
- Notification center could be a `@blecsd/notifications` plugin

This keeps the core library lean while enabling opt-in functionality.
